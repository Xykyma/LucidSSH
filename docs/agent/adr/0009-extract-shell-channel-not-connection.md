# Шов в `sessionManager.ts` проводится по каналу, а не по подключению

Решение (сессия `/grill-with-docs` по кандидату 02 архитектурного обзора, 2026-08-19):
при разрезе `sessionManager.ts` (1331 строка) выносится **конвейер вывода**
(`shellChannel.ts` + `commandReport.ts`), а **область подключения** (~600 строк:
`attemptConnect`, jump-туннель, host key, повтор пароля, переподключение)
остаётся на месте. `ShellChannel` получает в конструкторе уже открытый
`ClientChannel`, а не `ssh2.Client`.

Термины «Сессия», «Соединение», «Канал» — см. [CONTEXT.md](../CONTEXT.md).
Полная спека — `.scratch/shell-channel-extraction/spec.md`.

**Это ADR существует потому, что решение противоречит лежащему рядом документу.**
Исходный отчёт обзора (`.scratch/architecture-review-2026-08/spec.md`, кандидат 02)
прямо называет естественным швом «установку соединения (326–826)». Код после этой
работы будет выглядеть как незаконченный распил: вынесли меньшую половину, бо́льшую
оставили. Первый человек, который это заметит, захочет «доделать» — читать сюда,
а не переоткрывать.

Причины:

- **Резать надо там, где нет рычага.** У области подключения тестовый вход уже
  построен и работает: подменяемая фабрика `Client` (`__setClientFactoryForTest`)
  плюс алиас `attemptConnectForTest`, на них написано 18 из 24 существующих тестов.
  У конвейера вывода входа нет ни одного — чтобы добраться до него, тест обязан
  поднять фейковый `Client` → `attemptConnect` → `'ready'` → `openShell` и
  скормить маркеры в поток. Вынос подключения означал бы переписать 743 строки
  рабочих тестов ради нуля новой проверяемости.
- **Метрика «моков станет меньше» не выдержала проверки** и не была основанием.
  `errors/detector`, `content/loader`, `notifications/notifier`, `hosts/repository`
  и `config/store` нужны обеим половинам; суммарное число строк `vi.mock` в
  репозитории после разреза вырастет. Основание — достижимость конвейера, а не
  число моков.
- **Сто строк принятия решений не покрыты ничем.** `handleCommandFinished`,
  `recordCommand`, `checkShellUnavailable` содержат семь развилок (сигнал, пустой
  Enter, SET-05, `isNonErrorExitCode` из issue 03, ERR-06, ERR-07, HIST-07) и не
  имеют ни одного теста, тогда как листья под ними покрыты 33 кейсами
  (`errors/detector.test.ts`, `secrets/maskers.test.ts`, `history/repository.test.ts`).
  Это ровно тот расклад, который закрыл кандидат 01: каждая половина проверена,
  стык — ничем.

**Почему `ShellChannel` получает поток, а не `Client`.** Тест канала должен
писать `new ShellChannel({ stream: fakeStream, … })` и сразу кормить байты; при
передаче `Client` ему снова понадобился бы дублёр с колбэчным `.shell(cfg, cb)` —
то самое хозяйство, ради ухода от которого разрез и делается. Побочно это
правильно раскладывает две вещи: ветка ошибки `client.shell` выносит суждение о
Сессии («канал не открылся, но соединение есть»), а Канала в этот момент не
существует; дашборд — отдельный exec-канал на том же Соединении (DASH-02), к
потоку shell отношения не имеет. Цена — `openShell` остаётся в файле подключения
как 15-строчный вызов транспорта.

**Рассмотренные альтернативы:**

- *Вынести область подключения* (буквальное предложение отчёта) — отклонено по
  первому пункту причин.
- *Три файла: реестр / подключение / канал* — отклонено: реестр это ~70 строк,
  которые никто отдельно не тестирует и которые не несут ни одной зависимости;
  третий файл не решал бы ни одной задачи. Третьим файлом стал `commandReport.ts`
  по противоположному основанию — он несёт 9 моков из 13.
- *Свободные функции с `session: ManagedSession` первым аргументом* (самый дешёвый
  дифф) — отклонено: чтобы позвать такую функцию в тесте, всё равно пришлось бы
  собрать `ManagedSession` через `as unknown as`, то есть выигрыша по цели ноль.

**Следствие, которое легко нарушить.** Канал пересоздаётся на каждое открытие
потока — при переподключении и при эскалации через su/sudo. Поэтому `everConnected`
и `shellUnavailable` **остаются полями сессии**, а канал только сообщает о них
(`onOpened()`, `onShellUnavailable()`). `everConnected`, положенный внутрь канала,
сбрасывался бы ровно тогда, когда NOTIF-01 его спрашивает, — и потеря соединения
после переподключения перестала бы отличаться от неудачного входа.

**Что осталось за границей.** Кандидат 04 (объединение `FakeableClient` и
`FakeableTestClient` в общий `SshTransport`) числился в отчёте как «ложащийся на
02». Это было верно для варианта с выносом подключения; после настоящего решения
оба шва целиком остаются внутри нетронутой области, и 04 становится полностью
независимым кандидатом.

Позже 04 решён отдельно — [ADR-0017](./0017-open-connection-seam-up-to-ready.md):
из области подключения вынесено **одно Соединение до `ready`** (`connection.ts`),
написанное дважды — в `sessionManager` и в `testConnection`. Оркестрация остаётся здесь,
граница этого ADR не сдвигается.

Решение принято 2026-08-19.
