# Хостовое состояние живёт в хранилище хостов и подметается каскадом

Решение (сессия `/grill-with-docs`, 2026-08-26): `history.perHostDisabled` и
`dashboard.dismissedAlerts` уезжают из `config.json` в `hosts.db` — первое колонкой
`hosts.history_enabled`, второе дочерней таблицей `host_dismissed_alerts` с
`ON DELETE CASCADE`. Ручная сборка мусора при удалении хоста удаляется. Quick Connect
персистентного хостового состояния не получает.

Термины «Настройка» / «Внутреннее состояние» и статья «Что происходит с хостовым при
удалении хоста» — см. [CONTEXT.md](../CONTEXT.md). Родительское решение —
[ADR-0014](./0014-config-split-settings-and-state.md). Полная спека —
`.scratch/host-scoped-flags-to-db/spec.md`.

**Правило: значение, осмысленное только при существующем хосте, хранится там же, где
хост.** Оба поля были внешними ключами на таблицу хостов, положенными в JSON-файл.
Формально это работало; практически правило «не забудь подмести при удалении»
соблюдалось вручную и уже было соблюдено не везде — у `perHostDisabled` сборка мусора
написана (`ipc/hosts.ts:133`), у `dismissedAlerts` не написана вовсе, и записи по
удалённым хостам копились с релиза 1.0.0. Расхождение двух GC — не небрежность автора,
а предсказуемый исход: правило, которое некому применить кроме человека, применяется
через раз.

**Два поля переезжают в разные формы, и асимметрия — не оплошность.**
`history_enabled` — колонка в `hosts` и поле в `Host`: его пишет окно (тумблер в форме
хоста), это Настройка в смысле ADR-0014, и renderer обязан его видеть.
`dismissedAlerts` — отдельная таблица, в `Host` не входит: его пишет main, включая
self-clearing без участия пользователя (`ssh/dashboard.ts:255`), это Внутреннее
состояние, и «окно такого значения не видит вовсе». Положи мьюты колонкой в `hosts` —
они поехали бы в renderer с каждым `hostList`, то есть завелось бы ровно то зеркало,
от которого уходил ADR-0014. Отдельная таблица делает это невозможным схемой, а не
дисциплиной: поля нет там, откуда его можно случайно отдать.

**У Quick Connect нет хоста, значит нет и персистентного хостового состояния.**
Quick Connect работает под синтетическим `hostId: 0` (`ssh/sessionManager.ts:244`),
строки в БД для него нет и быть не может (`AUTOINCREMENT` начинает с 1). Сегодня mute
DASH-10 для такой сессии ложится в `dismissedAlerts[0]` — **один на все Quick
Connect-подключения разом**: замьютив «диск заполнен» на одном сервере, пользователь
глушит ту же находку на любом другом. Это и есть цена ключа без владельца: он схлопывает
разные серверы в один. После переезда кнопка «Больше не показывать» для Quick Connect
скрывается; крестик остаётся. Возможность не отнимается — перестаёт обещаться то, чего
не было: баннер и так одноразовый на сессию (`firstSuccessDone`), поэтому «до конца
сессии» — это ровно «до крестика», и вся ценность кнопки была в персистентности.
Прецедент того же жеста — вкладка серверных сниппетов, скрытая для Quick Connect
в 1.0.1 по той же причине.

**Рассмотренные альтернативы:**

- **Оставить мьюты в `config.json` и дописать им ручную сборку мусора** — отклонено.
  Это ровно то состояние, из которого тикет вырос: правило есть, соблюдается вручную,
  соблюдено не везде. Дописать второй GC — значит починить один экземпляр и оставить
  механизм, порождающий третий.
- **Обе величины колонками в `hosts`, мьюты — JSON-массивом в TEXT** — отклонено дважды.
  Кладёт Внутреннее состояние в объект, который окно получает целиком (см. выше). И
  воспроизводит исходную болезнь на уровень ниже: множество внутри строки БД снимается
  по одному элементу через «прочитать → распарсить → отфильтровать → сериализовать →
  записать» вместо `DELETE ... WHERE host_id=? AND issue=?`.
- **Колонка есть, но вычёркивается из `rowToHost`** — отклонено. Держится на том, что
  никто не допишет одну строку; отдельная таблица держится на том, что дописывать
  нечего.
- **Ключ мьюта по `address:port:username` вместо `hostId`, чтобы Quick Connect
  сохранил кнопку** — отклонено. Заводит вторую систему идентификации сервера ради
  подключения, которое по определению не запоминают, и оставляет мьюты без каскада —
  то есть без единственного механизма, ради которого затевался переезд.
- **Перенос мьютов отдельной функцией при старте приложения** — отклонено в пользу
  шага миграции `v3`. Отдельной функции понадобился бы собственный маркер
  «выполнено», которого в проекте нет ни одного, — а `user_version` именно им
  и является. Прецедент функциональной миграции с разбором старого представления и
  молчаливым отбрасыванием нерезолвимого — шаг `v2` (`hosts/db.ts:47-76`).
- **Тумблер истории заодно удаляет накопленную историю хоста** — отклонено. Настройка,
  стирающая данные побочным эффектом, — необратимое действие под видом обратимого.
  Аналогия с SNIP-07 играет против: там вопрос задаётся при удалении хоста, когда
  объект и так исчезает и что-то с его контентом сделать обязательно. Явная операция
  «очистить историю этого хоста» ушла отдельным тикетом
  (`.scratch/history-clear-per-host/spec.md`).
- **Расширить тикет на `snippets.host_id` и `history.host_id`** — отклонено по проверке,
  не по объёму. У сниппетов сборка мусора есть и намеренно не тихая (SNIP-07 спрашивает
  пользователя); записи истории обязаны пережить хост, рядом лежит `host_name`. Каскад
  через файл БД в SQLite невозможен физически, и оба случая от него не зависят.

**Полярность флага — положительная.** `history_enabled DEFAULT 1`, как у соседнего
`guard_enabled`, хотя исходное поле называлось `perHostDisabled`, а критерий приёмки
HIST-07 просил переключатель «не вести историю для этого хоста». Отрицательное поле
дороже всего в момент чтения условия: `!host.historyDisabled && cfg.history.enabled` —
двойное отрицание в горячем пути записи истории, ровно там, где отказ тихий: история
просто перестаёт писаться, и этого не замечают месяцами. Формулировка критерия правится
вместе с возвратом ✅ на HIST-07 — она описывала намерение, а не предписывала подпись.

**Канал переименовывается вместе с данными.** `config:dismiss-dashboard-alert` →
`dashboard:dismiss-alert`, хендлер из `ipc/config.ts` в `ipc/hosts.ts`. Оставить
префикс `config:` у канала, пишущего в `hosts.db`, — воспроизвести в слое IPC ту же
ошибку, ради которой заведён тикет: следующий читатель пойдёт искать эти данные в
`config.json`, потому что имя канала так сказало. Префикс взят `dashboard:`, а не
`host:`: канал про находку дашборда, хост в ней лишь адрес, а `host:*` в проекте
означает CRUD хоста.

**Границы, которые легко принять за недоделку:**

- **`history.perHostDisabled` не мигрируется.** Не по решению «отбросить», а потому что
  переносить нечего: писателей у поля два — сборка мусора (только удаляет) и всё. Пути
  `history.perHostDisabled` нет в allow-list `WRITABLE`, UI нет, дефолт `[]`. Значение
  может появиться только правкой файла руками.
- **Мьюты по удалённым хостам при миграции исчезают, а не переносятся.** Формально это
  потеря данных при обновлении; в CHANGELOG она не попадает — пользователь этих записей
  никогда не видел, они и есть предмет тикета.
- **Миграция читает `config.json` в обход `loadConfig()`.** Вынужденно:
  `mergeWithDefaults` выбрасывает ключи, которых нет в дефолтах, поэтому после выноса
  полей из `AppState` штатный загрузчик вернул бы пустоту, и «отбросить» стало бы
  решением по умолчанию, случайно. `hosts/db.ts` ценой этого узнаёт про формат
  `config.json` — знание одноразовое и мёртвое сразу после написания: оно про прошлый
  формат, который больше не меняется.
- **`EXPORT_VERSION` остаётся `1`**, хотя в экспорт хостов добавляется поле. Версию
  формата двигают, когда старый читатель ломается о новый файл или новый — о старый;
  здесь ни того, ни другого: старая сборка проигнорирует неизвестное поле, новая
  подставит `true` на его отсутствие. Поднятая версия при полной совместимости —
  ложный сигнал несовместимости.

**Принятая цена.** Форма `config.json` перестаёт быть единственным местом, где видно
всё пользовательское состояние приложения: часть его теперь в `hosts.db`, и чтобы
ответить «что мы про пользователя помним», надо посмотреть в два хранилища вместо
одного. Взамен исчезает целый класс ошибки — состояние, переживающее объект, к которому
относится, — и «не забудь подмести» перестаёт быть обязанностью человека. Страховкой
служит тест каскада: в SQLite нетривиальные миграции делаются пересозданием таблицы,
при котором легко потерять `ON DELETE CASCADE` и не заметить — ничего не падает, просто
снова начинает копиться мусор.
