# Доверие ключу хоста — свойство Соединения, а не Сессии

Решение (сессия `/grill-with-docs` по кандидату 05 архитектурного обзора, 2026-09-12):
на **каждое** Соединение действует одна и та же политика — сверка предъявленного
ключа с `known_hosts`, при несовпадении интерактивное решение пользователя
(SSH-03/04), запись в `known_hosts` только после явного accept. Применяется ко
всем четырём путям, открывающим `ssh2.Client`: сессия, Быстрое подключение (HM-11),
пробное подключение из формы хоста, оба хопа цепочки через jump-хост (SSH-05).

Машинка решения выносится из `sessionManager` в собственный модуль `src/main/ssh/`
с интерфейсом из двух функций — «запросить решение» и «применить решение»; логгер
соединения передаётся ей как необязательная зависимость.

Термин «Соединение» — [CONTEXT.md](../CONTEXT.md), раздел «Три уровня "подключения"».
Полная спека — `.scratch/host-key-decision/spec.md`.

**Почему это вообще решение, а не очевидность.** До него «при каждом подключении»
из SEC-03 и «до отправки пароля» из SSH-07 молча читались как «при каждой Сессии».
Под таким чтением оба Must проходили свои критерии приёмки, а кнопка «Проверить
соединение» открывала настоящий `ssh2.Client` к целевому хосту с `hostVerifier:
() => true` и отправляла туда пароль, набранный пользователем в форме. Формулировка
требований этого не разрешала; её просто применяли не к той сущности.

**Кандидат предлагал другое, и это не подтвердилось.** Отчёт описывал «три
реализации с разными ответами» и предлагал интерфейс `verify(address, port, key, mode)`
с режимами `interactive | strict`. Третьей реализации нет: путь настроек (SET-04)
ничего не проверяет — он показывает и удаляет записи, а разбор адреса берёт из
`parseHostToken`, точной обратной функции к приватному `hostToken` в том же
`knownHosts.ts`. Дублирования между двумя оставшимися путями тоже нет: strict — это
одна строка `matchesKnownKey(...)`, и сам `matchesKnownKey` и есть тот общий код,
ради которого предлагался модуль.

**Рассмотренные альтернативы:**

- **`KnownHostsPolicy` с параметром `mode`, как предлагал отчёт** — отклонено.
  Сигнатуры двух режимов не сводятся: strict отвечает синхронным boolean, интерактив
  уходит в renderer и возвращается решением через произвольное время, и ему нужны
  `requestId`, окно таймаута и отдельный вызов «применить». Общий параметр `mode`
  дал бы фасад, у которого половина аргументов осмысленна только в одной из веток.
- **Оставить целевой хоп теста без проверки, записав это осознанным компромиссом
  («тест — это ping+auth, не гарантия»)** — отклонено. Компромисс, который стоит
  пользователю его пароля, компромиссом не является; честная запись такого решения
  означала бы снять ✅ с двух Must навсегда, а не дописать комментарий в шапке файла.
- **Strict на целевом хопе теста (как было у bastion): пускать только уже известный
  ключ** — отклонено. «Проверить соединение» жмут при настройке **нового** сервера,
  которого в `known_hosts` заведомо нет; кнопка перестала бы работать ровно в том
  сценарии, ради которого существует. Для bastion этот аргумент не работал, потому
  что bastion по определению настраивается раньше как отдельный хост.
- **Обрывать тест до аутентификации: показать отпечаток как информацию, пароль не
  отправлять вовсе** — отклонено. Безопаснее всего, но кнопка перестаёт отвечать на
  вопрос, ради которого её жмут («правильные ли у меня креды»); рядом уже есть
  «Подключить», и отдельная кнопка, которая делает ping, дублирует его.
- **Сохранить strict-режим для bastion-хопа теста** — отклонено, режим удалён вместе
  с `matchesKnownKey` и `requireKnownHostKey`. Обоснование, на котором он держался,
  было записано в шапке `testConnection.ts`: кнопка отдала бы **сохранённый** пароль
  bastion серверу, подлинность которого не подтверждена, «причём пользователь этот
  bastion в форме даже не редактирует и подмены не заметит». Всё держалось на слове
  «не заметит»: под интерактивной политикой модалка показывает имя bastion, его адрес
  и отпечаток, и пароль уходит только после явного accept — гарантия становится той
  же, что в сессии, где этот же сохранённый пароль через этот же bastion уходит
  ежедневно.
- **Оставить машинку решения в `sessionManager` и экспортировать её наружу** —
  отклонено. Это развернуло бы ADR-0009, где доступ к `sessionManager` специально
  сузили до `sessionExists`/`hostIdOf` и удалили `getSession`. Плюс тестовая цена:
  `sessionManager.test.ts` требует 13 `vi.mock`, чтобы файл просто загрузился, и
  тесты решения по отпечатку унаследовали бы этот налог — а именно из-за него
  правило обязательного покрытия (§10 CLAUDE.md) на этот путь до сих пор не ставили.

**Дефект, который прятал strict на bastion.** `checkJumpHost` не требует, чтобы
bastion когда-нибудь открывали: jump-хостом назначается любой сохранённый хост.
Поэтому связка «завёл bastion → назначил его целевому → нажал Проверить соединение»
падала с `clog.jump.hostkeyUnknown` на конфигурации, где реальное подключение
работает штатно (в сессии bastion получает промпт). Кнопка проверки падала там, где
подключение проходит, — худший вид ошибки для целевой аудитории продукта.

**Принятая цена.** Пробное подключение теперь пишет в `known_hosts` ключ хоста,
который, возможно, никогда не будет сохранён. Прецедент принят раньше и осознанно:
Quick Connect (HM-11) делает ровно то же для `hostId=0`. Побочный эффект считаем
выигрышем, а не издержкой — сегодня пользователь, проверивший новый сервер кнопкой,
через минуту видит модалку первого подключения на ровном месте; после правки
решение принимается один раз.

**Границы, которые легко принять за недоделку:**

- **Событие NOTIF-03 «изменился fingerprint» теперь может прийти из теста.** Это
  намеренно: ключ действительно сменился, и повод для красного бейджа не зависит от
  того, какой кнопкой пользователь это обнаружил.
- **Модалка различает повод только подписью кнопки.** «Подтвердить и подключиться»
  из теста было бы неправдой — подключения не будет; заголовок, тело и подсказка
  SSH-08 остаются общими, потому что решение, которое принимает пользователь, ровно
  то же самое. Отдельная модалка под тест отклонена как дублирование.
- **`HostKeyPrompt.hostId` удалён.** Поле не читал никто; под тест нового хоста его
  пришлось бы заполнять нулём по конвенции HM-11, и мёртвое поле начало бы требовать
  объяснений в комментарии.
- **`knownHosts.ts` остаётся хранилищем.** `findKnownKey`/`addKnownKey`/
  `replaceKnownKey`/`parseHostToken` не трогаются: решение о доверии живёт этажом
  выше, и смешивать его с чтением и записью файла не нужно — именно это смешение
  кандидат и принял за «три реализации».
